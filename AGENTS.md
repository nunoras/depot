# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- The destination is the spec at https://github.com/nunoras/depot/issues/30, with the decisions behind it on the map at https://github.com/nunoras/depot/issues/29 and the tickets those two produced. Read the spec before changing behaviour; it owns the vocabulary, the state list and the v1 cut line.
- Rust workspace, one crate per layer: `crates/depot-core` (pure rules), `crates/depotd` (daemon), `crates/depot` (CLI). Gates: `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all --check`.
- `depot-core` is the one testing seam for the lifecycle rules, and it takes facts in and returns state plus intended actions out. It must stay free of filesystem, network, processes and wall clock, so anything time-shaped arrives as a fact field. It declares no dependencies; `crates/depot-core/tests/purity.rs` guards that and `README.md` states it.
- `crates/depot-core/tests/lifecycle.rs` holds one table per lifecycle rule. The dispatch resolution rules have their own table in `crates/depot-core/tests/dispatch.rs`.
- `crates/depotd/src/adapters/` holds the five boundaries depot talks to (boxr sessions, treehouse worktrees, the forge, role profiles, the Typesafe dispatch matcher). Each is a thin trait plus an implementation that speaks the real protocol; adapters hold no policy, because the rules stay in `depot-core`. `crates/depotd/tests/` has one contract test per adapter, driving the real implementation against a fake that reproduces the protocol's success, failure and malformed cases. `docs/adr/0002-adapters-behind-seams.md` records why.
- What depot requires of boxr, command by command and field by field, is recorded in `docs/boxr-contract.md`, along with the minimum boxr version (0.2.0). The capability probe refuses a boxr whose `--help` omits a required command. Launch passes the task role as `--kind` and omits `--account` when the machine-local profile leaves account empty (pi). Treehouse acquire always checks out a delivery branch named by `depot_core::delivery_branch` from the task title and intent, a `feat`/`fix`/`chore`/`refactor` prefix plus a title slug, suffixed on collision, and a detached worktree falls back to that same name at push time. Daily-driver open path: `docs/daily-driver.md`. First real boxr run notes: `docs/first-real-project-report.md`.
- Every state transition is driven by a fact, never by model prose. `docs/adr/0001-local-daemon-and-deterministic-facts.md` records why, and `CONTEXT.md` is the glossary for the domain language.
- Persistence and configuration live in `crates/depotd`: `Store` is the sqlite record of projects, tasks, dependency edges, attempts, questions, validations, forge state and the event journal, `ProjectConfig` is the machine-local `.depot.toml` holding project knowledge, ignored via `.git/info/exclude` on `project add`, and `Settings` is the machine-local `<depot home>/config.toml`. The two halves of that split never mix; `crates/depotd/tests/config_split.rs` guards it and `README.md` documents the layout.
- `render_checklist` is a pure function of a `ProjectState`. Checklist bytes are written only by depotd write paths (`add_project`, `Store::put_task`, and `Store::apply_fact`), never by hand. Same state, same bytes; `crates/depotd/tests/checklist.rs` asserts it, so nothing time-shaped or order-shaped may enter the render.
- No comments in code, no docstrings, no TODOs. Rationale belongs in the commit message, the ticket, or an ADR.
- The coordinator contract ships as versioned artifacts under `assets/` (policy prompt, kickoff, brief template), included in the binary with `include_str!` and rendered by `crates/depotd/src/coordinator.rs`. Nothing in them names a harness or a model: that comes from project config, and `crates/depotd/tests/coordinator.rs` asserts it.
- `Store::apply_fact` and `Store::apply_facts` (`crates/depotd/src/store/apply.rs`) are the one write path: reduce the facts in order, write the changed tasks, the coordinator row and the journal entries in one transaction, then the checklist. The batched form exists so the dispatch judgement and the task proposal it produced land together. The CLI and the daemon use it, and the actions it returns are the daemon's to execute. Task commands preflight the current task state before calling it: they refuse a transition the rules will not take, treat an already-reached end as a successful no-op, and never journal a fact they then claim as success.
- The journal is the inbox's source, joined to the current records: `depot inbox` reports the facts since the coordinator's read position while naming where each task stands now, and it splits them by who has to act. Fact kind names are the journal's vocabulary, declared in `crates/depotd/src/vocabulary.rs` as `FactTag`; a new `FactKind` breaks the build until the tag, the payload encoder and the inbox classify it.
- The coordinator session and its rotation rule live in `depot-core` (rules 12 to 14 in `crates/depot-core/tests/lifecycle.rs`), and the context size limit is machine-local (`coordinator_context_tokens`). A project's home scaffolds `docs/context.md`, which the coordinator writes and depot never renders.
- Dispatch is configuration, not a coordinator turn: `depot task add` takes an optional `--role`, and without one the judge in `crates/depotd/src/dispatch.rs` reads `[dispatch]` and `[[dispatch.rules]]` from `.depot.toml`, asks Typesafe one Choice question, and applies the confidence floor, the rule's role and its first candidate with the pure rules in `crates/depot-core/src/dispatch.rs`. The model sees only the rules' `when` strings plus a fixed neutral option, never a role, a candidate or a fallback. A rule with no candidates resolves through `[profiles]`, and the chosen profile is pinned on the task so a later rules edit never swaps a running task's model. The decision is a `task_dispatch_judged` fact (`source = model_judgement`) written before the proposal in one `apply_facts` transaction; every refusal is named and creates no task. `docs/adr/0004-model-matched-rules-resolve-in-code.md` records why.
- The Typesafe adapter keys from an owner-only `typesafe-key` file in the depot home under the same permission rules as the GitHub token, and the base URL is machine-local `typesafe_base_url`. No key means no request and the layer is off.
- The daemon loop (`crates/depotd/src/daemon.rs`) polls session status on each tick, reconciles worker liveness, launches workers for approved tasks, runs validation when workers submit, and delivers validated work (push and PR). It acquires an exclusive lock at startup to prevent multiple instances and performs recovery to transition in-flight attempts to `Unknown` state. Polling records the `Polled` fact but is the one fact kind the log suppresses (`logs_fact`). Liveness is throttled rather than deduped: a `WorkerLivenessChanged` fact is written when the observed value changes or when the last one for that task is older than 60 seconds, so `last_seen_at` keeps advancing for a healthy session without one fact per tick. The daemon enforces `run_duration_minutes` from the current attempt's `started_at` and records `RunDurationExceeded` once, and `reconcile_sessions` turns a terminal `limitHit` status into one `ProviderRateLimited` while any other terminal failure becomes a `WorkerSessionFailed` fact whose reason (`error`, else `captureError`, else a generic line) lands on `Task::failure` for the checklist and inbox. `Sessions::resume` calls `boxr resume --detach` and returns the new child id, and the daemon refuses a missing or parent id so the answer stays owed.
- Both binaries carry the package version and the git commit they were built from: `crates/depotd/build.rs` sets `DEPOT_BUILD_ID` with rerun rules for the HEAD file and the branch ref, `depotd::version_line` prints it, and `--version` answers on both. The daemon records that build id in the scope record `<depot home>/depotd.scope.json` beside the lock file, and `depot status` and the TUI warn when the running daemon was built from another commit. `depot daemon restart` (`crates/depotd/src/restart.rs`) writes `<depot home>/depotd.stop` naming the holder pid and start time, waits a bounded time for the lock, then launches the installed depotd beside the `depot` binary with the recorded project scope and appends its output to `<depot home>/depotd.log`; it reports success only once the scope record names the new pid with a heartbeat at or after the launch, and otherwise exits nonzero saying the daemon did not take the instance lock. A daemon honors a stop request only when the pid and the start time both match, so a recycled pid is never touched, and a scope record it cannot read is left alone. `scripts/depotd-supervisor.sh` runs depotd with rotation capped at 10 MiB and 3 backups; the log the CLI writes is never rotated. `docs/daemon-operations.md` owns the operator view.
- `depot artifact add <file>` copies a regular file into `<depot home>/artifacts` under a collision-free name and runs `[artifacts] publish_command` from `Settings` with `DEPOT_ARTIFACT_PATH` set, requiring exactly one http(s) URL on stdout. The file name never reaches the command line, and a failing command or an unusable URL keeps the staged copy and says where it is. depot hosts and serves nothing.
- `depot task wait` blocks until `TaskState::settles_a_wait` (waiting_on_question, pr_open, landed, failed or cancelled), polls at one second or slower, and never reads the inbox cursor. `depot project list` prints each project's path and resolved profiles, and `--kind` aliases `--role` on `task add`.
- Validation and describe both fetch the configured base to `refs/remotes/origin/<base>` before using it, so a stale or absent local base branch never changes the answer. `ShellValidation` checks out the submitted commit into a scratch worktree under the system temp directory, merges the fetched base there with `--no-commit --no-ff`, then runs the project gate on that merged tree. The scratch worktree is removed on every path, the worker branch and index stay untouched, and the submitted commit stays the delivered head. A conflict is a `validation_finished` with a nonzero exit; a fetch or checkout that never produced a runnable tree records `validation_failed` and holds the task. The fetched base commit is stored on the validation record and the `validation_finished` payload. `[pull_request] describe_style` is machine-local project text prepended to the describe prompt when nonempty, and the default prompt names no external skill.
- PR evidence is opt-in through `[evidence]` in `.depot.toml`: with a `command` set, `reconcile_evidence` runs it once per validated commit in the `PrOpen` worktree (with `DEPOT_EVIDENCE_BASE`/`DEPOT_EVIDENCE_RANGE` set) and reads `value<TAB>caption` manifest lines from stdout, where a value with a scheme is a URL used as-is and anything else is a local file path resolved against that worktree. Depot owns one replaceable `## Proof` section in the pull request body, delimited by the `<!-- depot-proof:start -->` and `<!-- depot-proof:end -->` markers: images render as markdown, every other URL renders as a bare URL so a GitHub user-attachment video embeds, and a local file renders a note that it cannot be attached to a pull request and needs a URL. Depot never uploads a file and never sends the API token to a github.com web endpoint, because GitHub's user-attachments endpoint needs a signed-in browser session depot does not have. A later describe refresh carries the section forward instead of erasing it (`crates/depotd/src/evidence.rs` holds the pure parse/resolve/render/merge logic and the `EvidenceRunner` seam tests inject). A run is journalled once per task and commit as `evidence_posted` or `evidence_failed`; `required = true` turns a run that produced nothing attachable into `Failed` plus `HoldForUser`, the default only notes it. A pull request body depot writes starts with the `<!-- depot-managed -->` marker; on adopting an existing pull request depot refreshes the title and body only when that marker is present, and otherwise leaves them alone apart from appending the Proof section. Depot never captures, hosts or drives a browser.
- Forge polling is confined to tasks in `PrOpen`, so an idle depot issues no forge calls at all; a poll records only a change (`pull_request_checks_changed`, `pull_request_merged`, `pull_request_closed_unmerged`), and a pushed branch whose pull request already exists at the forge is adopted, so `pull_request_opened` never means a second PR. `[pull_request] auto_merge` in `.depot.toml` is opt-in and consulted from the records every tick through `depot_core::auto_merge_due`, which requires passing checks and a head equal to the validated commit, so merging stays separate from permission to start dependent work (issue 12). A `pull_request_merged` fact whose head is not that validated commit is refused: the task is held for a person instead of landing, and "no validated commit at all" counts as a mismatch, so a merge never lands a revision depot did not validate. `reconcile_delivery` carries the push a `PrOpen` task still owes whenever its newest passing validation is not its branch head, so a push lost between the validation fact and the action is retried rather than leaving `validated_commit()` empty for the rest of the task's life. An automatic merge is asked for once per observed state: each attempt is recorded, and the next attempt is compared against the last one, so an observation identical to it is never asked again while a moved base or a moved head earns the next attempt. A failure records `pull_request_merge_refused` (the forge's reason, classified as the user's in `depot inbox` while the task is `PrOpen`) instead of only logging it. The reason is noted on the task and rendered as `auto-merge refused` in the checklist until the pull request lands or closes.
- Pending work is derived from the records on every tick, never from the action list of the fact that started it: `reconcile_start`, `reconcile_resume`, `reconcile_validation`, `reconcile_delivery`, `reconcile_forge` and `reconcile_leases` each carry one kind of outstanding work forward, and each has to be idempotent because the daemon runs it every tick. A fact the CLI wrote reaches its end this way, since the CLI executes no actions. Leasing a worktree, launching a worker and resuming a worker record a durable intent before their external call, and reconciliation resolves an intent with no completion instead of suppressing the work forever - the treehouse pool is the truth for a lease, so an acquire intent it confirms is completed and one it contradicts is retried, while a session state is never taken as proof a resume landed, so the resume is retried up to a bounded ladder and then held for a person; a launch leaves no session id to probe, so an uncompleted launch records `WorkerTurnUnresolved` and holds the task for a person. `docs/adr/0003-reconciliation-derives-pending-work.md` records why, and `crates/depot/tests/golden_path.rs` is the suite that holds it. `reconcile_leases` returns the worktree lease a task in a terminal state still owes: the records name it in `Task::release_pending`, the startup sweep also reads the treehouse pool for leases the records never named, a lease any attempt still names is left alone, a held release is re-probed only after a backoff, and one failing lease is logged without stopping the rest of the pass.
- `crates/depot/tests/golden_path.rs` is the end-to-end suite and the executable definition of done for v1: the real `depot` binary, a real git repository with a real remote, a scripted worker, a fake boxr child process, a local fake forge and a local fake Typesafe endpoint, with the daemon run tick by tick over the daemon binary's own adapters. Its dispatch scenarios live in `crates/depot/tests/support/dispatch.rs` and drive a real `.depot.toml` in the temporary project. `crates/depot/tests/support/` holds the fixture and includes the fakes under `crates/depotd/tests/support/`; `crates/depot/tests/fake_boxr.rs` is the fake boxr itself, built as the `fake_boxr` test target (`harness = false`) and located by the suite beside the test binary.

## Maintaining this file

Keep this file for knowledge useful to almost every future agent session in this project.
Do not repeat what the codebase already shows; point to the authoritative file or command instead.
Prefer rewriting or pruning existing entries over appending new ones.
When updating this file, preserve this bar for all agents and keep entries concise.
